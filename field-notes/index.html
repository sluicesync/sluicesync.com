Field Notes

War stories from building a correctness-first migration tool — the engine behaviors, wire-protocol edges, and silent-corruption classes we hit, and what we changed because of them.

sluice's first tenet is that a migration must never silently corrupt or lose data — a loud failure you can act on beats an exit 0 that quietly dropped four thousand rows. Living up to that means chasing down a lot of surprising database behavior: drivers that pick a different binary codec per column type, managed services with hidden query limits, replication phases that disagree with each other, precision edges that only bite above a specific integer. This section is where we write those up.

Field notes are evergreen engine-behavior documentation, not release announcements. Each one is a real thing we hit — most of them silent-corruption classes caught by fuzzing, battle-testing, or differential runs — with the mechanism explained, a repro you can run yourself, what sluice does about it, and the transferable lesson for anyone building on the same engines. Where the root cause is upstream (an open MySQL bug, a Vitess design choice), we say so and cite the public source; where it was our bug, we name it and link the fix.

None of these require sluice to reproduce — they are properties of Postgres, MySQL, Vitess, SQLite, and the wire protocols and drivers around them. If you move data between databases for a living, several of them will eventually be your problem too.

They're listed newest first, each dated to roughly when the work landed in sluice. The engine tag is just a signpost — the primary ordering is chronological, not by engine. The depth mark tells you what you're committing to — · quick note, •• field note, ● deep dive — and ★ marks the handful of flagship findings.

  • 2026-09-01Postgres● deep dive A Postgres function's name is not its identity — PostgreSQL identifies a function by (name, argument types), so a catalog read scoped by proname alone can resolve to a row nothing executes: gut the real 0-arg trigger function, plant a same-named 1-arg decoy carrying a healthy body, and a name-only audit grades the decoy and passes. It is permanent, too — CREATE OR REPLACE of the 0-arg function cannot remove an overload, so the obvious repair never clears it. And a function's definition is three catalog columns, not one.
  • 2026-08-31Postgres● deep dive Your event trigger fires for the DROP and sees zero rows — An event trigger on ddl_command_end fires for a DROP — and pg_event_trigger_ddl_commands() returns zero rows, so the loop body never runs. Dropped-object information is reachable only from the sql_drop event, through a different context function. Measured on PG 16.14 and 17.11: ALTER TABLE → 1 row, CREATE INDEX → 1, DROP INDEX → 0, DROP TABLE → 0. A WHEN TAG IN ('DROP TABLE', …) filter therefore reads as coverage while being incapable of producing a row.
  • 2026-08-27Postgres● deep dive ENABLE ALWAYS fires for everyone — The sequel to the trigger-capture blind spot: flipping capture triggers to ENABLE ALWAYS really does make them fire for replicated writes — even a subscriber's TRUNCATE, applied through a separate executor path, still fires an ALWAYS statement trigger, observed end-to-end on a real subscription. But Postgres gives a trigger no origin evidence, so “capture replicated writes, except my own applier's” cannot be built — and your own sync one hop upstream is just another replica-role writer. The safety boundary has to move from filtering rows to refusing topologies, keyed on what can recur, not what is currently running.
  • 2026-08-23SQLite & D1•• field note SQLite's format('%.17g') silently caps floats at 16 significant digits — SQLite's format() looks exactly like C's printf and silently isn't: its %g caps output at 16 significant digits — one short of the 17 a double needs to round-trip — and %.16g, %.17g, %.20g, %.25g all emit the same 16-digit render. ~46% of swept doubles came back a different double. Only the obscure ! flag lifts the cap.
  • 2026-08-22MySQL & Vitess•• field note Two MySQL replication wire formats disagree about padding — The classic binlog strips a fixed BINARY(N) column's trailing 0x00 padding, so CDC delivered 2 bytes where the snapshot delivered 8 — at exit 0. Vitess's VStream doesn't strip: full width on both its COPY and CDC legs, verified on a real cluster. The same tool needed opposite handling on its two MySQL replication lanes.
  • 2026-08-20MySQL & Vitess•• field note The same tool disagreed with itself about whether a TINYINT(1) is a boolean — MySQL's BOOL alias does not extend to UNSIGNED or AUTO_INCREMENT tinyint(1). The schema translator knew that; the VStream replication decoder answered the same question from the wire's own column_type string — and answered it differently. An auto-increment tinyint(1) primary key collapsed every value ≥2 to 1 on the change stream, while the cold copy was correct.
  • 2026-08-19MySQL & Vitess•• field note TINYINT(1) is a display width, not a value constraint — MySQL's BOOL is an alias for TINYINT(1), but the (1) is a formatting hint — the column stores the full signed 8-bit range. A legacy column holding 0–6 collapsed to true under the boolean mapping, at exit 0. sluice WARNed — and carried the collapsed value anyway. A warning you don't stop on is a footnote on the corruption.
  • 2026-08-18Postgres•• field note A Postgres domain has a different type OID on each of the two wires — On a regular query's wire a domain column reports its base type's OID, so drivers decode it with zero special handling. On the logical-replication wire, pgoutput reports the domain's own dynamic OID — with typmod -1, so even a varchar(10) base loses its length. The same driver round-trips the whole cold copy, then halts on the first CDC row.
  • 2026-08-17Cross-cutting•• field note Pushing NOT through a quantifier is the wrong De Morgan — Postgres stores x NOT IN (1,2) as a negation over a quantifier; MySQL keeps not in. A canonicalizer that simplifies NOT by negating the operator is exact for scalars and invalid across ANY/ALL — NOT (x = ANY S) is x <> ALL S, not x <> ANY S — so schema diff certified a gutted NOT IN constraint as in sync.
  • 2026-08-14Cross-cutting•• field note The catalog rewrote round(x), and the target lacks the overload it wrote — MySQL doesn't store your CHECK (round(d) >= -100000) — it materializes the default scale into the text, round(d,0). PostgreSQL has round(double precision) and round(numeric, integer) but no round(double precision, integer), so the faithfully-carried constraint dies at CREATE TABLE with 42883. The identical CHECK on a DECIMAL column migrates fine — which is exactly why the test corpus missed it.
  • 2026-08-27MariaDB•• field note The forensics table MariaDB doesn't have — MySQL session forensics — which connected session holds a binlog_format override? — is a two-table JOIN on performance_schema.variables_by_thread. On MariaDB that query dies with ERROR 1146: … doesn't exist, with performance_schema ON or OFF, because MariaDB's performance_schema never implemented the table — while under the OFF default the tables it does have answer empty instead of erroring. A runbook ported by syntax detonates at exactly the mid-incident moment it's reached for.
  • 2026-08-23Postgres•• field note A long-open transaction anywhere freezes your trigger-CDC — A gap-free trigger-CDC poll emits only provably-settled rows — txid below the current snapshot's xmin. Any open write transaction anywhere on the server pins that xmin, so the poll returns zero rows and the stream logs healthy-idle while replication lag grows without bound. Nothing is lost and nothing is wrong — and nothing says it's happening: a pinned-xmin stall is byte-identical to a genuinely quiet source.
  • 2026-08-22MySQL & Vitess•• field note Go's zero time.Time is a live wire against MySQL — go-sql-driver/mysql serializes any IsZero() instant as MySQL's invalid '0000-00-00' sentinel — and Postgres happily stores year-1 dates, which decode in Go to exactly time.Time{}. So a legitimate '0001-01-01' either false-refuses under strict sql_mode with an error naming a value the source never held, or lands silently rewritten under a relaxed one.
  • 2026-08-17MySQL & Vitess•• field note The same unsigned primary key is int64 to one reader and uint64 to the other — A match key bridging two readers of the same MySQL table must survive the readers decoding the same unsigned PK to different Go types — int64 on the binary protocol, uint64 from VStream. So the obvious hardening, a %T type tag on the key, is exactly backwards: it would split every unsigned PK and silently miss the repair. The bug that did ship was quieter still — a composite key joined by a bare NUL let two distinct rows collide, writing one row's floats into the other row's archived record, in a backup that verifies green.
  • 2026-08-27MySQL & MariaDB● deep dive The replica you can't detect is the replica that loses your writes — With log_replica_updates=OFF, a MySQL replica applies replicated writes without entering them in its own binlog — the cold copy is perfect, and the CDC tail silently misses the entire write stream the replica exists to carry. GTID arithmetic makes it churn rather than lag: purged = executed − binlogged, so the replicated GTIDs look purged instantly and every resume triggers a fresh resnapshot, forever. And the probe that should catch it hits a dialect trap: on MariaDB, bare SHOW REPLICA STATUS lists only the default connection — a named multi-source replica answers “I'm not a replica” to every MySQL-style question.
  • 2026-08-26Postgres•• field note FOR ALL TABLES doesn't mean all tables — Unlogged tables write no WAL, so logical replication can't stream them — and Postgres's two publication forms handle that in opposite directions: a scoped FOR TABLE publication refuses an unlogged table loudly, while FOR ALL TABLES silently leaves it out of pg_publication_tables. Mid-sync it's sharper: SET UNLOGGED on a scoped member errors; under FOR ALL TABLES the identical flip succeeds and the table silently drops out of the stream — after the cold copy included it, so the target freezes at the snapshot forever while everything reports green.
  • 2026-08-26Postgres● deep dive Postgres never logically decodes a table rewrite — A typmod-only ALTER COLUMN … TYPE numeric(10,1) on a numeric(10,4) column rewrites the whole table — rounding every stored value — while the replication slot decodes zero messages: Postgres rewrites into a transient relation that logical decoding deliberately skips. The only wire artifact is one number (the typmod) in the next RelationMessage, invisible to a classifier that compares type OIDs. And the same-type USING rewrite is strictly worse: content-identical on the wire, provably undetectable from the stream.
  • 2026-08-26MySQL & Vitess● deep dive MySQL never binlogs the cascade — Delete a parent row with ON DELETE CASCADE children and MySQL's binlog carries exactly one event: the parent's. The cascaded child deletes are never logged — the replica is expected to re-run the cascade through its own FK definitions. But nearly every CDC applier disables FK enforcement on apply, precisely to be free of row ordering — switching off exactly the mechanism MySQL delegated the cascade to. Child rows silently survive at exit 0; of four common target postures, only an unprivileged Postgres converges, by accident of privilege. Postgres WAL-logs its cascades; none of this arises there.
  • 2026-08-26MariaDB•• field note MariaDB's log_bin_compress makes the binlog size-conditional — Turn on MariaDB's log_bin_compress and the binlog becomes size-conditional: any row image ≥ log_bin_compress_min_len (256 B default) travels as a MARIADB_*_ROWS_COMPRESSED_EVENT_V1 — three event types most consumers' switches don't enumerate — while smaller rows keep the plain types. A consumer with a silent default arm loses rows conditioned on their size: small rows kept, big rows gone, and the GTID fold still advances the resume position past the loss. All three verbs — a big row's DELETE compresses too, via its before-image.
  • 2026-08-26Postgres•• field note Your trigger-based CDC can't see replicated writes — A plain CREATE TRIGGER never fires for DML applied under session_replication_role = 'replica' — which is how logical-replication apply workers run, and how replication tools (sluice included) apply their own writes to bypass FK enforcement mid-stream. The rows land, the change log stays empty, the sync exits 0. Sharpest twist: the privileged production applier is blind where the unprivileged dev one wasn't — it works in staging, then loses in prod.
  • 2026-08-19MySQL & Vitess•• field note A freshly copied table reports 16 KB, so the size gate sizes itself out — Right after a bulk COPY, a 36 MB PlanetScale table reported DATA_LENGTH = 16384 (16 KB) and TABLE_ROWS = 5,925 — the catalog statistics hadn't caught up. A size gate keyed off the just-copied target read three orders of magnitude low and never fired, so the safeguard was absent on exactly the platform it protects. Nothing errored; the threshold just never tripped. Size off the long-lived source, not the freshly-loaded target.
  • 2026-08-19MySQL & Vitess•• field note The scan-once index build that walls you, and the resume that re-issues it forever — Collapsing a table's index builds into one ALTER so InnoDB scans once is a real win — until a per-statement time limit. On PlanetScale a 12.8 GB table's four-index ALTER hit the ~900 s wall at 900,004 ms, and --resume re-issued the identical statement, so the build could never converge. The very property that makes the optimization efficient — one big statement — is what the wall kills; the fix splits it into one ALTER per index.
  • 2026-07-26Cross-cutting● deep dive Your usage is invisible in the API for exactly as long as it's free — The billing API omits every $0.00 line item, so a metered-but-unbilled resource returns nothing — and the metrics endpoint's per-pod counters rotate away underneath you, where the textbook increase() rule reads routine backend skew as counter resets and over-counts by 2.2×.
  • 2026-07-26Postgres•• field note Three alerts that could never fire, and nobody noticed because no wrong number was ever reported — A per-pod metric fan where Postgres carries only planetscale_role — no tablet_type, no container — so the selection cascade honestly refused, and a storage alert sat permanently inert. Replica lag was worse: neither engine emits a primary series, because a primary has no lag.
  • 2026-07-26MySQL & Vitess•• field note The transport said “please reconnect”; the driver reported “your request is malformed” — HTTP/2's polite drain — GOAWAY with ErrCode=NO_ERROR — arrives through gRPC as codes.InvalidArgument, because the code describes the envelope-parse failure rather than your request. A classifier that correctly treats InvalidArgument as terminal therefore kills an unattended stream on routine platform maintenance.
  • 2026-07-24Cross-cutting•• field note The retry budget whose only proof of progress lived in the database that was down — sluice persists its CDC apply position in a control table on the target — the standard exactly-once move, since the position write rides the batch transaction. But the retry budget's only reset path was a successful position read against that same target, so when the store was the outage, progress between outages was never credited: the second target outage of a stream's lifetime exited “budget exhausted” on its first failures despite hours of verified progress in between. Progress evidence must be gathered where the outage can't reach it — in memory, while healthy.
  • 2026-07-24MySQL & Vitess•• field note Your own next statement erases the warning — Under a relaxed sql_mode, MySQL coerces 300 into a TINYINT as 127 and tells you once — on the session diagnostics area, which the next statement clears. For a CDC applier whose position write shares the batch transaction, the statement that makes the batch durable is the statement that destroys the proof it was coerced.
  • 2026-07-24Postgres•• field note Your UNIQUE constraint survived the migration; its semantics didn't — NULLS NOT DISTINCT, DEFERRABLE, and WITHOUT OVERLAPS all land on the target as a plain UNIQUE — including Postgres→Postgres. Same name, same columns, and it quietly accepts rows the source would have rejected. Plus two catalog surprises: NULLS NOT DISTINCT isn't on pg_constraint, and WITHOUT OVERLAPS is PG 18, not 17.
  • 2026-07-24MySQL & MariaDB•• field note The CDC stream that reports green and applies nothing — Everyone “knows” row-based CDC needs binlog_format=ROW — the surprise is what a non-ROW source looks like from the consumer's side: nothing. A STATEMENT-format source cold-copies clean, then every change arrives as a QueryEvent the row dispatcher ignores — the target freezes at the snapshot, the position never advances past the cold-start anchor, the stream runs green, and shutdown exits nil. MIXED is the same class — and MIXED is MariaDB's platform default, so an un-tuned MariaDB source hits this out of the box.
  • 2026-07-23Postgres•• field note Quoted CREATE PUBLICATION preserves case; START_REPLICATION downcases it — Quoted DDL preserves case — but the name you pass to START_REPLICATION's publication_names option is parsed as an unquoted identifier list and folded to lowercase, so pgoutput looks up sluice_mypub, which doesn't exist. Nothing checks at stream start: the slot creates, the whole bulk copy runs green, the stream stays healthy while the source is idle — and the 42704 fires only inside the first change callback, arbitrarily delayed, or never on a quiet source. Validate replication-object names to ^[a-z0-9_]+$ (≤63 bytes) before creating them.
  • 2026-07-23Cross-cutting•• field note found=false is two different facts — A sync retry loop chose “force a clean re-establishment” vs “warm resume” through a (found bool, err error) read whose error it discarded — and both engines return found=false when the read fails, so “the target is down and I could not read the anchor row” was indistinguishable from “no anchor row exists,” and the destructive branch latched. The kicker: a pure reliability improvement made it reachable, by keeping the process alive through the outage window a terminal exit had always masked.
  • 2026-07-23Postgres•• field note The first durable flag — Pushing a sync predicate into a Postgres publication row filter quietly changes the flag's lifetime: --where stops being per-process configuration and becomes durable source-side catalog state that outlives every restart. Warm resume deliberately never re-ensures the publication, so a widened, changed, or removed --where would leave the server filtering on the stale predicate — unobservable client-side by construction, since no client belt can see rows the server never sends. The honest options for a durable filter: re-assert idempotently, or record-and-compare.
  • 2026-07-23Postgres•• field note Postgres NUMERIC stores NaN — and NaN sorts above Infinity — SQL comparison is three-valued, so mapping a NaN operand to UNKNOWN feels principled — but for sorting and range comparisons Postgres defines a total order in which NaN is greater than every other value. The surprise stacks: NUMERIC, the exact type, also stores NaN (plus ±Infinity in unconstrained columns since PG 14) — and NaN sorts above Infinity. A client evaluator that mapped non-finite values to UNKNOWN→drop destroyed changes the server had faithfully delivered, under a benign-looking DEBUG log.
  • 2026-07-23Postgres•• field note Postgres rounds your fractional seconds through a C double — PostgreSQL parses a timestamp's fractional seconds as rint(strtod(fraction) * 1000000) — the digit string goes through an IEEE-754 double before rounding, so the result is not exact decimal round-half-even: .0001255 becomes 125.4999… µs in the double and rounds to .000125, where exact half-even on the digits gives .000126. A textbook half-even reimplementation agreed on every hand-picked boundary value and silently diverged on ~0.1% of 7-digit fractions — hand-picked boundaries cannot gate a rounding mode.
  • 2026-07-23Cross-cutting•• field note Error text is data, error codes are contract — A retry classifier that text-scans the whole error string for transient wording can be flipped by the data: server error messages routinely echo row values, key values, and table names. The worst observed chain: a duplicate-key failure on a table named reparent_history matched reparent → retried → the tolerate-on-retry path swallowed the second 1062 as “the rows already landed” — the whole batch silently absent while the migration reported success. When a structured driver error is present, the code must decide alone.
  • 2026-07-23Cross-cutting● deep dive One literal, three verdicts — Hand three engines WHERE d = '2024-01-01 08:30' where d is a DATE column and you get three comparison semantics: Postgres casts the literal down to the column's type (time-of-day silently discarded — the row matches), MySQL promotes the column up to datetime and compares the full instant (no match), and MariaDB promotes like MySQL but truncates extra fractional digits where MySQL rounds half-up. One of the three-way splits is between MySQL and its own fork — and any system that evaluates one predicate in two places disagrees with itself exactly on the boundary.

  • 2026-06-22Cross-cutting· quick note A poller that re-reads all of history every tick — A backup broker rebuilt its entire lineage chain on every 30-second tick — ~2,000 object-store GETs per tick on a week-old stream, even when nothing had changed, with a tick that could outlast its own interval. Cost that grows with accumulated history, forever.
  • 2026-06-20MySQL & Vitess•• field note ENUM is an ordinal and SET is a bitmask on the wire — In a raw binlog row event a MySQL ENUM is its 1-based ordinal and a SET is a numeric bitmask; the member-name list lives only in the table definition. Decode without the schema and SET('a','c') becomes "5". Snapshot and VStream hand you text, so it hides until raw CDC.
  • 2026-06-18MySQL & Vitess· quick note Your primary key is only unique per shard — vtgate merges every Vitess/PlanetScale shard into one logical stream, but per-shard id ranges mean the same primary-key value legitimately exists on several shards. Copy them into one target table and the collisions silently overwrite — exit 0, rows short.
  • 2026-06-17MySQL & Vitess· quick note A whole transaction in one zstd binlog event — MySQL 8.0.20+ can pack an entire transaction into a single compressed TRANSACTION_PAYLOAD_EVENT. A reader without a handler applies nothing and freezes its position with no error — and the server zeroes the inner events' end_log_pos, so a naive resume restarts mid-payload and dies.
  • 2026-06-15Cross-cutting•• field note The zero value is a loaded gun — A config field that “defaults on” silently defaults off for every caller that didn't go through the CLI, because in Go every unset field gets the zero value. Twice, with real database consequences.
  • 2026-06-13MySQL & Vitess· quick note vtgate erases the throttle signal ★ — The one in-band flag that says “this stream is throttled, wait” is deleted before any gRPC client can see it, so a throttled stream is indistinguishable from a hung one.
  • 2026-06-13MySQL & Vitess· quick note A comment hid a TRUNCATE from CDC ★ — A leading -- comment on a TRUNCATE made a CDC reader miss it entirely; the source emptied, the target kept every row, forever.
  • 2026-06-11Postgres•• field note Replication slots don't die with your process — A slot is a promise the server keeps until you drop it; a crashed backup, a refused cold-start, and a week-one leak each pinned WAL on the source until the disk filled.
  • 2026-06-11Cross-cutting· quick note Rewriting the whole manifest, once per chunk — Every backup checkpoint re-wrote the entire manifest.json — and since the manifest grows with table count, the total work was quadratic: a measured ~78 hours at 100k tables. The fix's two obvious cousins are the same quadratic in disguise.
  • 2026-06-10Cross-cutting•• field note One JSON blob in one row is a quadratic write — Storing all per-table progress as a single growing JSON blob, re-upserted on every checkpoint, is O(n²) — and on Postgres the amplification lands somewhere specific: a new tuple version plus a re-TOAST of the whole value, every time, on one hot row.
  • 2026-06-09MySQL & Vitess· quick note The cold-start that buffered a whole table into swap — A 13 GB PlanetScale table drove the process to ~41 GB of RAM and got OOM-killed with zero rows written — because the VStream snapshot reader held the entire copy phase in memory. The buffer wasn't laziness; three engine behaviors forced it.
  • 2026-06-08MySQL & Vitess· quick note BIGINT UNSIGNED overflows both bigint and int64 — A MySQL BIGINT UNSIGNED reaches 2&sup6;⁴−1, past Postgres bigint's 2&sup6;³−1 — and past Go's int64, so the driver hands it back as a uint64 that a []byte/string-only decoder can't route into a numeric or text target. Even the documented recovery was broken.
  • 2026-06-07MySQL & Vitess•• field note Setting workload=olap silently truncated our chunked reads — A one-line fix to lift vtgate's 100k-row cap set workload=olap session-wide; the parallel chunked reader inherited it and each chunk streamed only a prefix, so a 1.5M-row migrate copied 7,536 rows and exited 0 with migration complete.
  • 2026-06-03MySQL & Vitess· quick note The transaction that lands in neither the snapshot nor the binlog — Capture the consistent snapshot and the binlog position as two separate statements, and a transaction committing between them falls into the gap — after the frozen read view, below the recorded offset. It's in neither the copy nor the CDC tail. FLUSH TABLES WITH READ LOCK closes the seam.
  • 2026-06-02Postgres· quick note Postgres text can't hold a NUL byte — text/varchar/char reject an embedded 0x00 with SQLSTATE 22021; MySQL char/text store it fine. Over COPY the rejection surfaces far from the offending row and reads cryptically — and stripping the byte would be silent corruption.
  • 2026-05-31MySQL & Vitess· quick note MySQL TIME is a duration, not a time of day — A MySQL TIME ranges -838:59:59 to 838:59:59 and models elapsed duration, not clock time. Map it to Postgres time by name and any negative or over-24-hour value has nowhere to go — the target is interval.
  • 2026-05-30MySQL & Vitess· quick note MySQL turned our emoji into '?' — MySQL substitutes ? for 4-byte UTF-8 in ENUM/SET labels at CREATE TABLE time regardless of column charset; the label is gone from the catalog before any client sees it.
  • 2026-05-30Cross-cutting· quick note One redaction flag, two engines, two behaviors — --redact randomize:int:100000,200000 into a SMALLINT column loud-refused on a Postgres target and silently clamped every row to 32767 on a MySQL one — turning an anonymization rule into a constant, and a compliance guarantee into a compliance failure.
  • 2026-05-28Postgres•• field note REPLICA IDENTITY FULL ate our UPDATEs — Building an UPDATE's WHERE over every old column works forever on int/varchar, then a jsonb value fails the equality round-trip, the UPDATE matches zero rows, and idempotency tolerance swallows the miss.
  • 2026-05-25Cross-cutting•• field note The replication stream never tells you the column default — Neither pgoutput nor the MySQL binlog carries a column's DEFAULT. Forward an ADD COLUMN … DEFAULT now() over CDC and the target re-evaluates the default independently — so every pre-existing row gets a different value than the source's backfill.
  • 2026-05-24Postgres•• field note CREATE IF NOT EXISTS is not a lock — CREATE TABLE/TYPE … IF NOT EXISTS does a catalog pre-check and then an insert, and the two steps aren't atomic. Race the same name from two connections and one gets a unique_violation on pg_class — from the statement that reads like it can't fail.
  • 2026-05-23Postgres•• field note proto_version lets you parse streaming; only streaming='on' emits it — Two pgoutput knobs are easy to conflate, and the gap between them hides a silent-loss shape: if streaming ever activates and each chunk commits as its own transaction, a dropped StreamAbort leaves the pre-abort rows durably on the target — extra rows no checksum diff will catch.
  • 2026-05-22Postgres•• field note A Postgres LSN means nothing without its timeline — Resume a logical-replication slot after a PITR or a promotion and the same LSN points into a different WAL reference frame — the source streams from it happily and events are silently skipped. MySQL gets this right for free with GTIDs; Postgres's raw LSN carries no provenance.
  • 2026-05-20Cross-cutting· quick note BIT crosses the wire as bytes, and the engines disagree on layout — MySQL hands BIT(N) back as ceil(N/8) right-justified big-endian bytes; Postgres surfaces bit as a '0'/'1' text string. Carry the raw bytes between them and the value is silently corrupted — the ASCII of the digits, not the bits.
  • 2026-05-17Postgres· quick note The pgx codec that flattened numeric[][] ★ — A driver that selects its binary codec per target OID turned a 2×2 matrix into a flat four-element array, on byte-identical code that round-tripped int[][] perfectly.
  • 2026-05-15Cross-cutting· quick note Count your bytes, not your rows — A batch size tuned for narrow OLTP rows — 5,000 rows, under 10 MB — quietly pins hundreds of MB the moment the workload is MB-scale TEXT, BYTEA, JSON, or geometry. The streaming paths were fine; only the two accumulators blew up.
  • 2026-05-10Cross-cutting· quick note {}: two characters, two types — {} is an empty array in Postgres and an empty object in JSON; []byte("{}") is genuinely ambiguous, and for nine releases the MySQL writer resolved it the wrong way.
  • 2026-05-08MySQL & Vitess· quick note One INSERT is three binlog events (or four) — A single-row INSERT lands in the binlog as three events (BEGIN / WRITE_ROWS / XID), plus a spurious empty BEGIN/COMMIT per new connection. If you size a rollover bound by INSERT count, budget 4× — and Postgres counts differently again.
  • 2026-05-07Postgres•• field note Every HA knob on, and the slot still vanished at failover — Patroni slot-sync on, sync_replication_slots on, hot_standby_feedback on — and a logical slot that hadn't advanced during the sync window was still lost on promotion. The idle slot is the fragile one.
  • 2026-05-05MySQL & Vitess· quick note parseTime governs the query protocol, not the binlog — parseTime=true on the DSN makes the query driver return time.Time — but the replication stream hands temporal columns back as raw strings regardless. The first TIMESTAMP row killed the CDC pump, and the silent-channel-close looked exactly like a network stall for two release cycles.
  • 2026-05-05MySQL & Vitess•• field note One LOAD DATA can't load a BLOB and a JSON column — A BLOB needs CHARACTER SET binary or the server rejects its first non-ASCII byte; a JSON column rejects its input under CHARACTER SET binary. One statement-level clause, two columns that demand opposite answers.
  • 2026-05-04MySQL & Vitess•• field note MySQL won't match a JSON column by bind parameter — WHERE json_col = ? matches zero rows whether you bind the value as a string or as bytes — MySQL won't cast the parameter to JSON. On a CDC UPDATE, replay-idempotency tolerance turns the zero-row match into silent divergence.
